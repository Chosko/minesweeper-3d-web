# Task 88 — Steamworks binding spike

Target: claude+human

## Goal
Settle the open questions of feature `steam-desktop-host`: which Node
binding to Steamworks implements the adapter's Steam side —
steamworks.js extended with the leaderboard and shared-file calls, or
another binding — and whether the Steam overlay renders reliably over the
Electron window, with which window and GPU settings. The spike runs inside
the packaged Electron build, including the native module building against
Electron's runtime.

## Acceptance criteria
- Each candidate is checked against the adapter's full capability list
  (identity, presence, achievements, leaderboards with details arrays and
  all three download scopes, shared files write/share/download/attach,
  overlay) inside a packaged build on Windows with the Steam client
  running; the result is a capability-by-candidate table.
- The spike checks whether replacing a shared file under the same name
  keeps an earlier leaderboard attachment readable.
- `.claude/domain/features/steam-desktop-host.md` records the chosen
  binding, the capabilities it lacks (which stay reported unavailable) and
  the overlay's window and GPU settings, in place of its two open
  questions; `.claude/domain/features/steam-leaderboards.md` records the
  shared-file replacement outcome in place of that open question and, when
  replacement breaks earlier attachments, states the new-name-per-best rule
  it already describes. Nothing else in either document changes.
- Spike code that is not kept is deleted; the chosen binding is added to
  `desktop/package.json`.

## Decisions
- Settled here: the binding, the overlay settings
  (`.claude/domain/features/steam-desktop-host.md` § Open questions) and the
  shared-file replacement behaviour
  (`.claude/domain/features/steam-leaderboards.md` § Open questions). Both
  documents are normally `/architect`'s; this task updates them for exactly
  this and for nothing else.
- The binding decision also belongs in
  `.claude/domain/technical-direction.md`, which is `/product-design`'s and
  is not edited here: name it under *Follow-ups* for `/product-design`.

## Manual interventions

⚠ REQUIRES MANUAL INTERVENTION — pause implementation at these points and
walk the user through them on a Windows machine with the Steam client;
wait for their confirmation and verify the outcome before continuing:

1. After each candidate's spike build is packaged: the user runs it on
   Windows from the Steam client with a test account, runs the capability
   probe screen, and opens the overlay with Shift+Tab. Verify the probe's
   log file the user returns lists each capability's result.
2. After the shared-file probe: the user checks the test leaderboard entry
   in the Steam client still opens the earlier attachment. Verify against
   the probe log.
