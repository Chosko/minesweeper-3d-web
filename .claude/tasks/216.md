# Task 216 — Theme switch keeps every font weight the new theme declares loaded in Chromium

Target: claude

## Goal
The theme applier (`js/themes/applier.js`) loads the incoming theme's
stylesheet, then each of its declared font files through
`document.fonts.load`, and only then removes the old stylesheet. In
Chromium, that switch leaves the new theme's font weights that the page
has not drawn yet unloaded again, so text first drawn later in such a
weight — a canvas number on the board, a heading on a screen not yet
shown — falls back or waits for a late load, breaking the applier's
contract that a switch resolves only once the theme's fonts are in. A
fixture theme declares no fonts, so this shows only with a real theme that
declares several weights, and it must be fixed before the first real
second theme ships.

## Acceptance criteria
- After a theme switch resolves in Chromium, every font file the active
  theme's registry entry declares (each family, style and weight) reports
  loaded — `document.fonts.check` true for its spec and its `FontFace`
  status `loaded` — whether or not any element uses that weight yet, and
  it stays loaded after further switches away and back.
- A browser test proves it with a test-only theme that declares at least
  two weights of a font served from `tests/fixtures/themes/` (a new fixture
  theme, or the fixture theme given fonts if no other test relies on it
  declaring none): switch to it, check every declared weight without
  drawing it, switch back to *Joyful tiles*, check *Joyful tiles*' declared
  weights the same way, and draw text in an undrawn weight to a canvas with
  no fallback. The test fails without the fix.
- The fix is in the applier (or the theme stylesheet's `@font-face`
  handling it relies on), keeps the switch's no-half-applied-frame and
  failure contracts (`tests/theme.test.mjs`'s switch and failure tests
  still pass), and keeps the board art hand-off waiting for the number
  font as it does today.
- The cause is named in the task's closing report. When task 214 already
  fixed this as the cause of a theme-switch flake, this task's report says
  so and adds only the test above if 214 did not.
- `.claude/context/app-shell-kit.md`'s passage on the theme applier states
  how fonts stay loaded across a switch, if the fix changes what it says.

## Decisions
- **Proof with a test-only theme**: no real second theme exists yet, and
  this task must not ship one, so a fixture theme with real font files
  carries the proof.
