# Task 14 — Storage interface and document versioning

Target: claude

## Goal
Build the core of feature `platform-storage`: the one storage interface
callers persist through — named documents of plain data stored as
`{ version, data }` — with document registration and the upgrade chain that
brings an older document to its current version on load, over a pluggable
backend.

## Acceptance criteria
- `register(name, currentVersion, upgrades)` declares a document before it is
  loaded; loading or saving an unregistered name is a programming error.
- `load(name)` is asynchronous and returns the upgraded data, or nothing when
  the document does not exist. An older document runs every upgrade step in
  order and is saved back at the current version; a newer one than the game
  knows is refused, reported to the owner, and left untouched.
- `save(name, data)` is asynchronous, writes the whole document at its
  current version and reports success or failure, never throws.
- A corrupt or unreadable document is reported as missing and kept aside
  (not overwritten) until the owner saves a new one.
- The interface sits over a backend abstraction (read, write, keep-aside,
  available); an in-memory backend exists for tests, and the storage layer
  caches nothing.
- Node tests cover registration, every upgrade path, the newer-version
  refusal, corrupt documents, and failed saves.
