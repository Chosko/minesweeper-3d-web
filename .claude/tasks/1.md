# Task 1 — Token sheet with light and dark values

Target: claude

## Goal
Build the design-token sheet of feature `design-tokens-and-themes`: one
stylesheet declaring every token — palette, typography, spacing, radii,
elevation, motion and z-layers — as a CSS custom property, with the light
values on the root and the dark values under the dark theme attribute. The
existing shell variables are folded into it under semantic token names so the
current screens keep their look in the light theme, and every colour token
meets the feature's contrast contract in both themes.

## Acceptance criteria
- `css/tokens.css` declares the full token set the feature document lists:
  surfaces, ink, accent, success, danger, warning, focus ring; font families,
  size scale, weights and a tabular-figures token for timers and counters;
  spacing scale; radii; elevation shadows; motion durations and easings; the
  z-layer order of overlays.
- Every colour token has a light value on `:root` and a dark value under the
  dark theme root attribute (`[data-theme="dark"]` on `<html>`); token names
  are semantic, never named after a hue.
- Values are low-fidelity: the light values derive from the current look
  (pale sky-blue, deep-blue accent, dark navy ink); the dark palette,
  elevation shadows and motion durations and easings are simple placeholder
  values, the dark ones meeting the contrast contract. No value is taken
  from the high-fidelity designs.
- `css/style.css` reads the tokens instead of its own `--sky`, `--ink`,
  `--blue`, `--card`, … variables, and the existing screens look unchanged
  in the light theme.
- `index.html` loads `css/tokens.css` before `css/style.css`.
- A Node test parses `css/tokens.css` and asserts, for each theme, that body
  text against its surface meets 4.5:1 and large text and essential UI glyphs
  meet 3:1, and that every colour token has both a light and a dark value.
- The 3D scene's palette in `js/render.js` / `js/textures.js` is untouched.
- `.claude/domain/features/design-tokens-and-themes.md` records the settled
  typeface choice in place of its open question. Nothing else in the
  document changes.

## Decisions
- Low-fidelity pass: the token structure, names and both themes are
  complete, but every value that is a visual-design judgement is a plain
  placeholder; the high-fidelity values come from the approved designs in a
  later pass, and those designs are not an input to this task.
- Typeface: keep the current system font stack (`--font` / `--mono`) as the
  typography token values; a bundled typeface brings licence and web-build
  size cost for no gameplay gain, and swapping later changes only values,
  not structure. Settled here: the feature document's open question on
  typeface. `.claude/domain/features/design-tokens-and-themes.md` is normally
  `/architect`'s; this task updates it for exactly this and for nothing else.
- The dark theme attribute is `data-theme` on the document root, with values
  `light` and `dark`; the feature document requires one root attribute and
  leaves its name to implementation.
