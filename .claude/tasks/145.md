# Task 145 — Focus containment in overlays

Target: claude

## Goal
Keep keyboard and controller focus inside the overlay that is open, so Tab,
the arrow keys and the D-pad never reach the screen behind it. This is row
W-26 of `docs/UX_REVIEW.md` § Approved scope and work plan (Area: Input,
Size: Small, Phase 4) and it closes **P-43** (§ Input methods; minor, major
for screen-reader users): focus is not contained in overlays. Tab from the
Controls panel reaches the blurred menu behind it, from the pause and results
cards it reaches the HUD Pause button, and from the pause confirmation it
reaches the Look sensitivity slider under it. Approved solution: set `inert`
on every other top-level section while an overlay is open, or wrap Tab at its
edges. The overlays this task covers are: **the Controls modal, the pause
card, the pause confirmation, the results card, and the replay viewer over a
board** (its controls, with the 2D board and its HUD hidden behind it). The
work serves keyboard and screen-reader players.

## Acceptance criteria
- **Inert behind the overlay** (P-43): while one of the overlays above is the
  topmost open layer, every other top-level section of the page is `inert`
  (the overlay itself, and the status toast, are not); when it closes, the
  sections it made inert are live again and the next layer's containment
  applies. Concretely: with the Controls modal open the main menu is inert;
  with the pause card or the results card open the overlay bar (`#hud`, its
  Pause button included) and the board layers are inert; with the replay
  viewer open over a finished Classic 2D board the board layer and its HUD
  are inert.
- **The confirmation contains the pause card** (P-43): while the pause
  confirmation (`#pause-confirm`) shows, the rest of the pause card — the
  Look sensitivity slider and every other control outside the confirmation —
  is inert too; Cancel or Back lifts it.
- **Tab wraps where `inert` is not available**: when the browser has no
  `inert` (`'inert' in HTMLElement.prototype` is false), Tab from the last
  focusable control of the open overlay goes to its first, and Shift+Tab from
  the first goes to its last; with `inert` available no Tab handler changes
  the browser's own order.
- **One owner of `inert`**: the containment and the context-lost screen set
  and lift `inert` through the same code, so leaving `ctxlost` never lifts an
  `inert` an open overlay still needs, and the context-lost screen behaves as
  today (its reload and Back to menu, the menu inert behind it).
- **The D-pad walk respects the containment**: the controller's collection of
  a layer's focusables (`padFocusables` in `js/main.js`) skips controls inside
  an `inert` subtree, so with the confirmation open the D-pad never reaches the
  slider, and every move (`padNav`, `padActivate`, the default-focus
  fallback) stays inside the open overlay. Task 144's DOM-order fallback and
  task 122's arrow keys use the same collection, so they inherit this
  whichever lands first.
- **Focus restore on close is kept**: closing the Controls modal (close
  button, backdrop click, Esc, the controller) focuses the menu's Controls
  button (`#menu-help`); cancelling the confirmation refocuses the pause
  card's default (Resume, or Play again once the game ended); Back from the
  replay viewer to the results screen focuses Play again (`#r-again`); every
  screen change still hands focus to the screen's `defaultFocus`.
- **Tests first**:
  - `tests/shell-router.test.mjs` pins the DOM-free helpers added to
    `js/shell/navigation.js`: which top-level sections are made inert for a
    given open overlay (all but the overlay and the toast), and the Tab wrap
    (last → first, Shift+Tab first → last, no change in the middle).
  - A new Playwright check `tests/shell-focus-containment.test.mjs` (skipped
    when Playwright or chromium is unavailable) opens each overlay — the
    Controls modal, the pause card, the pause confirmation, the results card,
    the replay viewer over a finished Classic 2D board — presses Tab and
    Shift+Tab more times than the overlay has controls and asserts focus never
    leaves it (never the menu, `#hud-pause` or the Look sensitivity slider
    under the confirmation); repeats the walk with `inert` removed from the
    page's prototype to exercise the Tab wrap; drives a faked controller's
    D-pad through the confirmation and asserts the slider is never focused;
    and asserts each focus restore listed above.
- **What not to break** (`docs/UX_REVIEW.md` § Decisions taken): the
  confirmations that say "It will count as a loss"; Esc and the controller's
  back button closing the Controls modal or the confirmation before anything
  else; held-button suppression across screen changes; every existing walk
  reaching the same controls inside its overlay.
- `.claude/domain/features/game-shell.md` § Shell navigation states the
  settled point — while an overlay is open, the rest of the page is inert (Tab
  wraps at its edges where `inert` is unavailable), and the pause
  confirmation contains the pause card the same way — in every passage that
  describes which layer takes input. Nothing else in the document changes.

## Decisions
- **Out of scope: screen-reader announcements.** P-58 (a live region for the
  board, the results announcement) and the rest of P-56 to P-60 and I-16 are
  dropped by decision 17 of `docs/UX_REVIEW.md` § Decisions taken
  ("Accessibility settings: Not now"). This task adds no live region, no
  announcement and no board text alternative.
- **`inert` first, Tab wrap as the fallback.** Both are named by P-43's
  approved solution; `inert` also hides the background from screen readers,
  which a Tab wrap cannot, so it is the primary mechanism and the wrap runs
  only where `inert` is missing.
- **The toast stays live.** `#toast` is a polite status region; making it
  inert would silence the notices it already gives (controller connected,
  saves failing), so it is never part of the inert set.
- **One `inert` owner.** `showContextLost` / `hideContextLost` toggle `inert`
  today; a second writer would let one lift the other's state, so both go
  through the containment helper.
- **Settled here (`.claude/domain/features/game-shell.md` § Shell
  navigation):** the document says the topmost visible layer takes input and
  leaves keyboard Tab containment unstated; this task settles it as above.
  `.claude/domain/features/game-shell.md` is normally `/architect`'s; this
  task updates it for exactly this and for nothing else. A further design
  decision met at implementation time is not covered: leave that passage
  untouched and name it under *Follow-ups* as a precise follow-up.
- **Related, not preconditions:** task 144 (Controller walk, pad-aware
  Records and viewer, haptics) adds the DOM-order fallback over the same
  focusables and lists P-43 as out of its scope; task 122 (Menu keyboard
  navigation and browser Back) routes the arrows through the same path. The
  containment lives in the shared collection, so the order they land in does
  not matter.
