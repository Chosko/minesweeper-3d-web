# Task 86 — Page platform selection, capability flags, overlay pause and the quit flush

Target: claude

## Goal
Make the game page aware of the host, for feature `steam-desktop-host`: at
start-up the platform layer looks for the bridge and selects the Steam or the
browser implementations, publishes capability flags the rest of the game
reads, keeps the latest Steam state, turns overlay activation into the
shell's existing automatic pause, answers the host's flush request before
quit, and drives the desktop window from the page: the title bar's drag
region, Minimise and Fullscreen / Windowed, and — in windowed mode — the
window's size, which is the screen's frame at its natural size laid out
against the display's work area (`shared-screen-layout` § Architecture,
Screen frame).

Everything but the window's size is already built (commit `f7c592c`); what
remains is the windowed-mode sizing, which waits on the available area and
the natural screen sizes (tasks 289, 290, 291).

## Acceptance criteria
- `js/platform/index.js` selects once at start-up: bridge present → Steam
  implementation slots (storage, replay store, leaderboards, achievements)
  that later features fill; absent → the browser implementations and local
  stand-ins. No module outside `js/platform/` tests for Electron or the
  bridge. *(built)*
- Capability flags — desktop host, Steam present, achievements,
  leaderboards, shared files, cloud — are derived at start-up and updated
  from Steam state events; callers subscribe to changes. *(built)*
- An overlay-activated event pauses a started, unfinished game through the
  same path a window blur takes in the pause controller. *(built)*
- A flush-requested event awaits every registered flush hook (pending
  saves) and answers the host; the host waits for that answer bounded by a
  short timeout before shutting down. *(built)*
- With the desktop-host flag on, the title bar's Minimise and Fullscreen /
  Windowed call the bridge's window actions, the button showing the
  Windowed icon while fullscreen and the Fullscreen icon otherwise, and the
  title bar is the window's drag region. *(built)*
- Windowed, the page draws no backdrop: the frame sits at the window's
  edges, its rounded corners over the transparent window. The page reports
  the frame's size through `window.setContentSize` on every screen change
  and every change of the frame's size (the board choice panel opening, a
  board loading), never from the window's own size; during 3D play the
  frame is the whole work area.
- The host resizes the window to the reported size, never past the work
  area of the display it is on; a window moved to another display is laid
  out against that display's work area and resized to it.
- Fullscreen shows the frame at its natural size on the backdrop; leaving
  fullscreen restores the windowed size for the current screen.
- The web build behaves exactly as before: no bridge, browser
  implementations, every capability flag off; the title bar's window
  buttons do nothing, and no size is reported.
- Node tests cover the size reports with a fake bridge — a screen change, a
  frame resize, no report on the web; a desktop run shows the window
  following the main menu, a board choice with its panel opening, a game
  and 3D play, with no shrinking step down. A desktop run shows the overlay
  signal pausing a game.

## Decisions
- **Re-planned for the frameless desktop window** (design changelog
  2026-10-23): the page side of the window actions lives with the bridge
  client here, and waits on the title bar (task 282).
- **Re-planned for natural screen sizes** (owner decision, 2026-10-26): the
  first pass left the content size unreported because sizing the window to
  a frame laid out against the window fed back on itself; the layout now
  reads the available area (task 289), so the size can be reported.
- **Built in `f7c592c`**: the capability flags keep logged-on state beside
  them rather than in them — going offline switches no feature off; Steam
  calls reject with `offline` for callers to queue or degrade.
