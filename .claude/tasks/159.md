# Task 159 — Registry-driven theme applier with run-time switch and board module hand-off

Target: claude

## Goal
Replace the light/dark theme applier with the applier of feature
`theme-system`: before first paint it applies the stored theme from the
registry, and at run time it switches themes with no unstyled or
half-applied frame, then hands the new theme's board module to its
subscribers. It also carries the failure contract: a theme that fails to load
falls back or stays put and tells the player once.

## Acceptance criteria
- **Pre-paint.** A classic script (replacing `js/theme.js`) runs in `<head>`
  before any stylesheet paints: it reads the stored theme id from the saved
  settings document, maps it (unknown or absent → the default; `light` or
  `dark` → `joyful-tiles`), inserts that theme's stylesheet as a
  render-blocking `<link>` and sets the root `data-theme` attribute. It reads
  the registry's id → stylesheet mapping without importing an ES module (a
  small generated or mirrored table the registry test keeps in step with
  `js/themes/registry.js`). The interim static link and fixed attribute of
  task 158 are removed.
- **Applier interface** (ES module): the active id; `setTheme(id)` resolving
  once the theme is fully applied — new stylesheet loaded, board module
  imported, its fonts loaded (`document.fonts.load`) — and only then flipping
  the root attribute, removing the old stylesheet and notifying; rejecting
  with the previous theme still active when a file fails to load;
  `onThemeChange(listener)` called after the switch with the new id and its
  board module. A listener that throws does not stop the others.
- **Board module hand-off.** The applier imports the active theme's board
  module at start-up and on every switch and hands it to subscribers; no
  renderer imports a theme directly.
- **Token reader.** `js/tokens.js` reads the active theme's computed tokens
  and notifies through the new applier's change notification; the scene
  palette and the Records history chart keep working.
- **Failure contract.** A non-default theme whose files fail at start-up
  falls back to the default and tells the player once (the existing notice
  style); a failed switch keeps the current theme and tells the player once;
  the default theme failing to load shows the existing fatal card.
- **Tests** in `tests/theme.test.mjs`: the pre-paint mapping (unknown,
  absent, `light`, `dark`, a registered id), the stylesheet inserted before
  first paint, a switch that never shows two themes' attributes or no
  stylesheet (browser test switching between `joyful-tiles` and a test-only
  second theme registered from a fixture), ordering of load → flip → remove →
  notify, rejection on a failing file with the old theme active, the default
  failing → fatal card, listener isolation, and the token reader following a
  switch.
- `globalThis.msTheme`'s existing consumers (`js/main.js`, the settings
  applier, the gallery) are moved to the new interface in this change.

## Decisions
- **A mirrored id → stylesheet table for the pre-paint script**, kept in step
  with the registry by a test, because a classic pre-paint script cannot
  import the ES registry without delaying first paint.
- **A fixture theme** (test-only, registered by the test, never shipped)
  exercises the run-time switch, since *Joyful tiles* is the only shipped
  theme.
- **Settled design detail** (`.claude/domain/features/theme-system.md`
  § Architecture, *Theme applier*; § Interfaces, *Applier*, *Failure
  contract*): the mirrored table and the fixture theme. The feature document
  is not edited here; task 162 records what holds at ship time.
