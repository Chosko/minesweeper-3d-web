## Goal
Let the keyboard move through the shell's screens the way the controller
does, and make the browser's Back step back inside the game instead of
leaving it. This is row W-05 of `docs/UX_REVIEW.md` § Approved scope and work
plan (Area: Shell, Size: Small, Phase 1). It closes P-07 and P-61 of that
document. Today the arrow keys do nothing in the menus and board choice —
only Tab moves focus, eight stops between Beginner and Back — while the
Records picker does use arrows, and Settings' Back button sits 1,423 px down
the page (P-07, Minor, keyboard players). And the browser's Back button, and
a mouse's back button, are not bound: on any screen they leave the site for
the previous page, wherever the player is, instead of stepping back inside
the game (P-61, Major, everyone on a browser, worst mid-game). The approved
solutions: map the arrows to the same focus moves the D-pad uses, show
"Esc: Back" beside every Back, make Settings' Back sticky (P-07); push a
history entry per screen so Back steps back inside the game — board choice
to menu, Records to where it came from, pause mid-game — and only the main
menu lets Back leave the site, keeping the leave guard for a started game
(P-61).

## Acceptance criteria
- **Arrows move focus like the D-pad** (P-07): on the main menu, the
  placeholder screen, the Classic 2D and 3D board choice screens, the ready
  card, the pause card (its actions, its confirmation and its settings
  shortcuts), the results card, the controls modal and Settings, ArrowUp,
  ArrowDown, ArrowLeft and ArrowRight move focus to the control the D-pad's
  spatial search (`pickInDirection`, through the same path as `padNav`)
  picks in that direction inside the topmost layer, Left/Right moving across
  a row. With nothing focused in the layer, the first arrow focuses the
  layer's default focus, as the D-pad does. Arrows held down repeat as the
  browser's key repeat delivers them. The keyboard path shows the kit's
  keyboard focus ring (`:focus-visible`), not the controller's `pad-nav`
  ring.
- **Controls that own an arrow keep it** (P-07): a range slider keeps
  Left/Right for its value and Up/Down move focus, as the D-pad treats it; a
  number or text field keeps Left/Right for its caret and Up/Down move focus
  out of it; a segmented choice on these screens (Settings' choices) keeps
  Left/Right for its selection and Up/Down move focus to the control above or
  below. Any arrow a control has already handled (`defaultPrevented`) is left
  alone. Records — its picker and mode switch keep their arrow handling
  unchanged — the replay viewer's keys, the Classic 2D board's cursor and the
  3D game's keys are untouched.
- **"Esc: Back" beside every Back** (P-07): a `ui-text--muted` hint reading
  exactly "Esc: Back" sits beside each button Esc triggers: the Back buttons
  of both board choice screens, the placeholder, the ready card, Settings,
  Records and the replay viewer (controls and failure message), the results
  card's Back to menu and the context-lost screen's Back to menu. The pause
  card's Back to menu gets none, since Esc resumes there. The hint is not a
  focus stop and meets the contrast contract in both themes.
- **Settings' Back always reachable** (P-07): Settings' Back stays visible
  without scrolling at any scroll position — a sticky action row at the
  bottom of the Settings card's scroll area — in a 1280 × 800 window and at
  phone width, never covering a focused control (focus moves scroll it into
  view above the row). Back still returns to the screen Settings was opened
  from.
- **One history entry per stacked screen** (P-61): the browser's session
  history mirrors the router's back stack — `SHELL.go` that stacks a screen
  pushes an entry (`history.pushState`), a `replace` replaces it, and an
  in-app Back or an unwind to a stacked screen consumes the matching entries,
  so the history depth above the main menu always equals the stack's depth.
  The URL never changes (state only, no hash or path), so the deploy's 404
  redirect and a reload are unaffected; a reload opens the main menu as
  today.
- **Browser and mouse Back step back inside the game** (P-61): a `popstate`
  back runs the shell's Back for the current screen through `shellBack`, as
  Esc does: board choice → menu, Settings and Records → the screen they were
  opened from, the placeholder → menu, a fresh board's ready card → its board
  choice, results → menu, the replay viewer → its `returnTo`, the
  context-lost screen → menu; the controls modal or the pause confirmation
  closes first. On the board (3D `playing`, Classic 2D `classic-2d`) it
  pauses through `pauseGame` as an asked-for pause (source `button`), in
  pointer-locked 3D play too. During a game it never resumes and never
  leaves: on the pause card and on a started game's ready card the browser's
  Back keeps the game where it is, and during the 3D end delay it does
  nothing; each of these restores the consumed entry, so the next Back
  behaves the same. Leaving a started game stays the pause card's Back to
  menu with its "It will count as a loss" confirmation. A mouse's back
  button is covered by the same path, since the browser turns it into a
  history back.
- **Only the main menu lets Back leave** (P-61): on the main menu, with the
  stack empty, the browser's Back leaves the site for the previous page —
  also after a reload whose session history still holds this page's entries
  from before it (those entries are walked past, never shown as screens). A
  browser Forward never shows a screen: it is undone.
- **Leave guard kept** (P-61): the `beforeunload` guard (`guardLeave`) is
  unchanged — armed at game started, removed at finished, abandoned or
  failed, bypassed by the context-lost reload and the 3D end delay — so
  closing or reloading the tab during a started game still asks.
- **Tests first**: `tests/shell-history.test.mjs` pins the history sync
  against a fake history and router (push on go, replace on replace,
  consumption on in-app Back and unwind, `popstate` routed to Back, the
  restored entry on the board, the pause card and the end delay, nothing
  pushed on the menu, the post-reload walk-out, Forward undone);
  `tests/shell-router.test.mjs` pins the arrow-key helpers in
  `js/shell/navigation.js` (key → direction, which focused control keeps
  which arrow); `tests/components.test.mjs` pins the segmented choice's
  Left/Right-only mode, the "Esc: Back" hint's markup beside each Back and
  its contrast in both themes; `tests/settings-page.test.mjs` pins the
  sticky Back row. A Playwright test (skipped when Playwright or chromium is
  unavailable) walks the main menu, the 2D board choice, the pause card and
  Settings with arrows alone, checks Settings' Back is in the viewport after
  scrolling to the top and the bottom, and drives `page.goBack()` from board
  choice to menu, from Records back to results, from a started Classic 2D
  game to its pause card (twice, staying paused), and from the main menu off
  the page.
- **What not to break** (`docs/UX_REVIEW.md` § Decisions taken): the
  confirmations that say "It will count as a loss"; the last-choice memory;
  the live custom-form validation; release-to-act; Esc and the controller's
  back button behaving as today; the held-button suppression across screen
  changes; the pause card's 500 ms Esc rule after a lock release.
- `.claude/domain/features/game-shell.md` and
  `.claude/domain/features/settings.md` state the agreed design change — the
  browser's Back (and a mouse's back button) is a Back input like Esc on
  every shell screen, pausing on the board, never resuming or leaving during
  a game and leaving the site only from the main menu, with the back stack
  mirrored in the browser's session history — in every passage that stated
  the old one, and settle the arrow keys as the keyboard's spatial focus
  moves, the "Esc: Back" hint and Settings' always-visible Back. Nothing
  else in those documents changes.

## Decisions
- **Design change agreed (user decision, 2026-10-12):** settled by prior
  instruction — `docs/UX_REVIEW.md` P-61, approved without condition under §
  Approved scope and work plan (row W-05).
  - `game-shell.md` § Scope and non-goals ("Back on Esc and the controller's
    back button") and § Data and state, "Navigation contract" ("Esc and the
    controller's back button always mean Back or Pause") name two Back
    inputs; the browser's Back, and a mouse's back button through it,
    becomes a third with the same meaning, except that during a game it
    never resumes and it leaves the site only from the main menu.
  - `game-shell.md` § Data and state, "Shell state" keeps the back stack in
    memory only; it is now also mirrored as one same-URL session-history
    entry per stacked screen. Nothing is persisted, and a reload still opens
    the main menu.

  Settled here, without conflict: the arrow keys as the keyboard's spatial
  focus moves (`game-shell.md` § Scope, "focus order"; § Architecture,
  "Shell navigation"); the "Esc: Back" hint beside each Back; the leave-page
  guard unchanged (`game-shell.md` § Scope); Settings' Back kept visible by a
  sticky action row (`settings.md` § Architecture, "Settings page"). Those
  two documents are normally `/architect`'s; this task updates them for
  exactly this and for nothing else. A further design decision met at
  implementation time is not covered: leave that passage untouched and name
  it under *Follow-ups* as a precise follow-up.
- **Browser Back never resumes a game.** P-61 says Back pauses mid-game;
  Esc on the pause card resumes, but a browser Back pressed twice must not
  pause and then resume, and must not leave a started game without the
  confirmation, so on the pause card and a started game's ready card it
  holds the game in place.
- **Same URL, state only.** Entries carry the stack depth, not a screen
  route, so no deep link to an inner screen exists, GitHub Pages' 404
  redirect is untouched and a reload behaves as today.
- **History sync is its own DOM-free module** (`js/shell/history.js`), given
  the router and a history object, so it is unit-tested like the router;
  `js/main.js` wires it to `window.history` and `popstate`.
- **Browser Back is an asked-for pause with the existing `button` source**,
  the overlay pause button's, so the pause controller gains no new source
  and an unstarted board opens the card as Esc does.
- **Arrow scope.** "Menus, board choice, pause card and Settings" is read as
  every shell layer the D-pad walks except the boards, Records and the
  replay viewer, which have arrow handling of their own. Up/Down leave a
  slider, a field or a segmented choice, mirroring the D-pad, so arrows
  alone never trap focus.
- **Sticky, not duplicated.** P-07 says sticky; one Back keeps one focus
  stop and one default.
- **"Esc: Back" only where Esc does that.** A hint beside the pause card's
  Back to menu would lie, since Esc resumes there. The hint is keyboard copy
  only; device-aware glyphs belong to task 119 (row W-01, P-42).
- **Boundaries.** P-41 — the D-pad walk skipping the 2D custom form's
  fields and switch and Records' Watch and Pin buttons, the DOM-order
  fallback, each table row's Watch as a stop — is row W-25's. The
  single-column layouts, Settings' two- or three-column layout included
  (P-69), are row W-30's. Tasks 119, 120 and 121 also edit `js/main.js`,
  `index.html` and `css/style.css`; no ordering is required, so whichever
  lands later merges around the other.
