# Task 2 — Theme applier and token reader

## Goal
Add the two runtime pieces of feature `design-tokens-and-themes`: the theme
applier, which sets the root theme attribute before first paint and switches
it at run time, and the token reader, which gives Canvas renderers the active
value of a named token and notifies them when the theme changes.

## Acceptance criteria
- A theme applier runs before first paint (loaded from `index.html` ahead of
  the module graph), reads the stored theme through a synchronous getter,
  falls back to Light when the value is absent or not `light` / `dark`, and
  sets the root attribute; no screen flashes the wrong theme on load.
- The applier exposes `setTheme(light | dark)`, which sets the attribute and
  notifies listeners; an unknown value is treated as Light, never thrown.
- `js/tokens.js` exposes `token(name)`, returning the resolved value of the
  named token for the active theme from the token sheet's computed values
  (no second copy of the values), and `onThemeChange(listener)`, firing after
  the attribute changes and returning an unsubscribe.
- An unknown token name returns a visible fallback colour and logs once in
  development.
- The 3D renderer never subscribes to theme changes.
- Node tests cover the fallback rules, `setTheme`, listener notification and
  the unknown-token fallback, using injected document and storage stubs.

## Decisions
- Until the settings feature exists, the stored-theme getter reads nothing
  and the applier applies Light; the settings feature wires its stored value
  into the getter and calls `setTheme` on change. This keeps this feature a
  reader of the preference, never its writer.
