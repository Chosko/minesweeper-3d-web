# Task 53 — 3D state view and the large-board memory check

Target: claude

## Goal
Add the 3D state view of feature `3d-board-graph` — the read surface the 3D
renderer, picking and HUD consume, served from the shared engine — and
measure whether a 100 × 100 × 100 game on the shared engine fits within the
memory the 3D engine uses today, settling the feature's open question.

## Acceptance criteria
- A read-only view over a 3D game exposes per cell number, revealed, flagged
  and hidden; the phase, exploded cell, mines left and a change counter; and
  the cells changed since the last read, drained by a single consumer.
- The view mirrors the read surface `js/render.js`, `js/picking.js` and the
  HUD read from `js/logic.js` today (typed arrays by linear index, a change
  counter, a drained dirty set), so those modules only change where they
  obtain the game.
- Node tests cover the view after reveal, flag, chord, hide and un-hide, and
  the drain semantics.
- The memory of a 100 × 100 × 100 game (graph, engine state, hidden flag,
  counts) is measured against `js/logic.js`'s `Game` on the same board, and
  `.claude/domain/features/3d-board-graph.md` records the measured figures in
  place of its open question. Nothing else in the document changes.

## Decisions
- Settled here: the feature document's open question on large-board memory,
  by measurement. `.claude/domain/features/3d-board-graph.md` is normally
  `/architect`'s; this task updates it for exactly this and for nothing else.
  If the shared engine exceeds the old engine's memory, the figure is
  recorded as measured and the size consequence is named under Follow-ups,
  not decided here.
